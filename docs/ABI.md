# Long After Dark — host / engine / module ABI

This is the contract our Windows host must honour, recovered by our own
disassembly of the binaries in `<assets>/win/FILES` (the PC side of the After
Dark 4.0 Deluxe CD). It complements `DESIGN.md` (architecture) and
`API_SURFACE.md` (every imported function, counted and classified).

Every fact, count and address below was verified on those Deluxe binaries.
The other releases the host runs (After Dark 10th Anniversary, After Dark
3.2, Totally Twisted and The Simpsons) reach their modules through the same
two entry points (§2.2, §3.4). What differs for them (their own engine
builds, the AD 3.x host they shipped with, and the native AD3 bridge that
stands in for OLDMOD16 where a disc has none) is in `PACKAGES.md` §7. Input,
module buttons and the modules' saved state are in `INTERACTION.md`; how
every module makes sound, and how the host plays it, is in `AUDIO.md`.

**Status marks.** Every fact is marked **VERIFIED** — with the address in our
binaries that shows it — or **UNVERIFIED-LEAD** (from third-party notes in
`research/win/aw11-notes` / `research/win/refs`, which carry no open-source
license and were used only as pointers). Where a lead turned out wrong, §6 says
so.

**Address notation.** PE: virtual address at the image's preferred base
(`AFTERDAR.SCR`, `ADXPL510.DLL` and every Borland `.AD` prefer `0x400000`).
NE: `segment:offset` inside the file's own segment numbering (`1:0ec8`).
Listings that show every address quoted here are regenerated by
`research/win/pedis.py` / `research/win/nedis.py` into `research/win/dis/`
(gitignored; see §7).

## 0. What the host must do (summary)

**AD4 lane (pe32)** — load `ADXPL510.DLL` + one `.AD` (both relocated: all
prefer `0x400000`), resolve `_Module@4` then `Module`, fill one 348-byte
`AD_MODULE32`, and call `int __stdcall Module(AD_MODULE32*)` with messages
`0 SELECTED → 2 PREINITIALIZE → 3 BLANK → 4 DRAWFRAME… (9 PAINT on expose) →
5 CLOSE → 1 DESELECTED`. A return of 3 means "send 2 and 3 again" (SDK-built
modules never return it — they restart internally — but Psycho Deli returns
3 from every PAINT, §2.5); any other non-zero is a fatal error whose text is
at block `+0x50`. Fill `+0x14` (the `.AD`'s `HMODULE`) before message 0, and
let `GetModuleHandleA("adxpl510.dll")` + `GetProcAddress(…,
"SETTHEEXCEPTION")` resolve (§2.2). The module paces
itself from `timeGetTime`; control values are plain ints the host writes into
block `+0x40` at any time (no message). Sound is DirectSound (loaded
dynamically; IMA-ADPCM through MSACM32) and the MCI sequencer (§2.12). With
sound on, our host emulates all three over its audio engine; with it off,
`dsound.dll` is not found and MCI has no device, and the module runs silent
(`AUDIO.md` §7).

**Classic lane (ne16)** — do what `OLDMOD32.DLL` did, but as emulated far
calls straight into the real `OLDMOD16.DLL`: `SETADPALETTE16` ×4,
`LOADADMODULE16`, then `MODULEMESSAGE16(2,…)` once per frame, and
`SETMODULECTRLVALUES16` when controls change; `UNLOADADMODULE16` at the end.
`OLDMOD16` builds the AD3 `AD_SYSTEM`/`AD_MODULE` blocks, loads the module
and `AD_SND.DLL`, and calls the AD3 entry
`int FAR PASCAL MODULE(int msg, HDC hdc, HGLOBAL hADSystem)`. `OLDMOD16` has
no NE entry point: our NE loader must call its exported `DLLENTRYPOINT`
(reason 1) after loading it, or its two blocks are never allocated (§3.2). Only 12 of the
Deluxe disc's 61 Classic modules use `ADXPL300.DLL`; the rest draw with plain Win16 GDI.
The 16-bit lane additionally needs INT 21h/1Ah, selector `0x40`, VGA port
reads, x87 and 386 operand-size prefixes (§3.6).

**Both lanes** — every clock read must advance virtual time: engines and
modules busy-wait and calibrate CPU speed on the clock inside a single call
(§4). Both need x87; the flat lane also needs `0x67` (16-bit addressing of
`FS:[0]`/`FS:[4]`, CX-based `jcxz`) because of the Borland RTL (§4).

## 2. AD4 lane (Win32)

### 2.1 Loading

* **VERIFIED `AFTERDAR.SCR 0x4022d1`** (AD4 module class, vtable `0x40f040`
  slot 1) → `0x402107` fills the block (§2.3) → `0x402b9b` snapshots mixer
  volumes → `hdcSaved = SaveDC(hdc)` → `0x404850`:
  `SetCurrentDirectoryA(<HKLM Path>)` (`0x4047f6`), `LoadLibraryA(path)`,
  `GetProcAddress(h, "_Module@4")`, else `GetProcAddress(h, "Module")`
  (strings `0x4107f0`/`0x4107e8`); `FreeLibrary` if neither resolves.
* **VERIFIED** the host never touches `ADXPL510.DLL` itself: the engine is
  pulled in by the module's import table (21 of the 22 AD40 modules import it;
  `PSYCHO.AD` — Borland, with the same RTL — and the MSVC-built `STARRYNI.AD`
  are standalone). Our loader resolves `ADXPL510.DLL` from
  `FILES/AD40` for the Deluxe disc, and from the module's own package for
  the other releases (`PACKAGES.md` §7.2).
* **VERIFIED `0x40460c`**: module kind is sniffed from the file with
  `CreateFileMapping`: `MZ` + `NE` → 2 (Classic, `OLDMOD32` path), `MZ` + `PE`
  → 3 (AD4), else 4 (the host's built-in placeholder module at `0x402cec`).
* **Engine init exports.** `CheckADXPLVersion(1, name, buf)` (stdcall, 3 args)
  is called by *each module's* `DllMain` on attach, not by the host — **VERIFIED
  `TOASTERS 0x41eb0b`**; on failure the module shows
  `"Library Version Problem with %s"` and fails to load. The engine's
  `CheckADXPLVersion` (**VERIFIED `ADXPL510 0x42b5dc`**) succeeds iff the first
  argument is 1. `DllEntryPoint` is imported by all 21 modules but never called
  (bound only; the loader must still resolve it).
* **DLL entry (Borland RTL) — VERIFIED `ADXPL510 0x410000`, identical in every
  Borland `.AD`:** on `DLL_PROCESS_ATTACH` it saves the **two dwords just below
  the thread's stack base (`FS:[4]-8`, `FS:[4]-4`, `0x410064..0x410075`)**,
  probes `GetProcAddress(GetModuleHandleA(NULL), "__GetExceptDLLinfo")`
  (`0x4406bf`; must return NULL), runs the RTL startup (`0x4451f8`:
  `GetCommandLineA`, `GetEnvironmentStrings`, `GetStartupInfoA`, std handles,
  `SetConsoleCtrlHandler`) and then writes the two dwords back
  (`0x4100a8..0x4100bd`). A per-image attach counter (`ADXPL510 [0x45006e]`)
  makes a **second** `PROCESS_ATTACH` of the same loaded image fail (returns 0
  after a "Nonshared DATA segment required" message — `GetVersion()` bit 31 only
  picks the Win32s wording of that message, `0x410034..0x41005c`). So: deliver
  `PROCESS_ATTACH` exactly once per mapped image, and map a fresh image to
  reload. *(abi-review corrected: this is not a Win32s gate on the first
  attach.)*

### 2.2 Entry point

`int __stdcall Module(AD_MODULE32 *block)` — **VERIFIED**: call site
`AFTERDAR.SCR 0x402371..0x40237a` pushes one pointer (`lea eax,[esi+0x128]`)
and does not pop it (callee-cleans); the export `_Module@4` of `STARRYNI.AD`
is the MSVC stdcall decoration of a 4-byte argument list; Borland modules
export plain `Module` (entry `TOASTERS 0x41e4cb`, `ret 4`).

Every call the module makes first: `hdc = block->hDC;
SetViewportOrgEx(hdc, 0, 0, &old)` and, before returning,
`SetViewportOrgEx(hdc, old)` (**VERIFIED `TOASTERS 0x41e4df/0x41e4fb`,
`0x41ead9`**); then `SetUpModuleIdentity(theirModuleVar, block)` and
`SetUpMiscStatics(hdc)` (**VERIFIED `0x41e578`, `0x41e598`**) — the engine
takes the DC from that argument (`theirDeviceContext`, `ADXPL510 0x42b637`),
not from the block.

**`SETTHEEXCEPTION` — VERIFIED (abi-review).** Before dispatching, every
SDK-built module (the 21 that link the engine) calls
`GetProcAddress(GetModuleHandleA("adxpl510.dll"), "SETTHEEXCEPTION")` once,
caches the pointer and calls it on every `Module()` entry (`TOASTERS
0x41e484..0x41e4c4`, called from `0x41e535`); the export clears the engine's
pending exception code (`ADXPL510 0x41bed6`). If the lookup fails the module
`_dprintf`s "Error setting \"other\" theException" (and retries on the next
call) and goes on; the engine's pending exception code is then never cleared
(effect not traced further). Our
`GetModuleHandleA` must find the loaded engine by that lower-case file name
and `GetProcAddress` must resolve engine exports by name.

**Non-SDK dispatchers — VERIFIED (abi-review).** `PSYCHO.AD` has its own
10-entry table (`0x4100e7..0x4100f6`): 0/1/2/3/4/5/9 handled, 6 = button,
**7/8 ignored**; it reads `+0x14` (as its instance) and `+0x18` on every call
and never writes `+0x14` — the host must fill `+0x14` before message 0
(AFTERDAR does, `0x40235b`). `STARRYNI.AD` (`0x1000102c`) handles only
2/3/4/5 and returns 0 for everything else; it reads `+0x18`, `+0x2C..+0x38`
and `+0x40..+0x48` directly (clamping the control values).

So the only live input path in the original AD4 saver is keys (7/8) plus the
engine polling `GetAsyncKeyState`/`GetCursorPos` itself (`UserInput`,
`ADXPL510 0x413502`, `0x41354b`). Our host should send 7/8 for `KEY` lines
and may send 21/24/27/30 for `MOUSE` lines (handled by the SDK dispatcher even
though the 1996 host never sent them).

**Return values — VERIFIED (restart semantics corrected by abi-review).**
Host side: `0` = OK; `3` = restart — the host re-sends 2 then 3
(`0x4023ff` → `0x4020b5`, which sends 3 only if 2 returned 0) and uses *that*
result; the host treats any final non-zero as fatal: it formats `"%s: %s"`,
unloads the module and falls back to its built-in module (`0x401c97`).

Module side, SDK dispatcher (all 21 engine-linked modules; `TOASTERS
0x41e959..0x41eae6`, same shape in the other 20 per
`research/win/abiverify/modscan.py`): the dispatcher reads
`AfterDarkModule::theirResult` (`ADXPL510 0x450920`) and resets it. If it is 3
(`PortableModule::WantRestart`, `0x42bd40`) the dispatcher **handles the restart
itself** — deletes the module object, sets a flag so the next DRAWFRAME
re-creates it and blanks (`0x41e75f`) — and returns **0**
(`0x41e969..0x41e98e`). Any caught `FarThrow` returns **2** with
`ErrorMessage(code)` copied to `+0x50` (`0x41ea26..0x41eac9`). So SDK modules
only ever return 0 or 2.

`3` does reach the host from **`PSYCHO.AD`**: its PAINT (9) handler runs its
CLOSE code and returns 3 (`0x411a84`), so every expose re-runs
PREINITIALIZE + BLANK. Its PREINITIALIZE returns 2 with its own `+0x50` text
when `GetDeviceCaps(hdc, NUMCOLORS)` is 1..16 (`0x4111f4..0x411236`) — report
NUMCOLORS 20 (or −1). `STARRYNI.AD` always returns 0.

### 2.7 Timing

* **VERIFIED:** the host never sleeps between frames; it runs the loop on a
  dedicated thread at `THREAD_PRIORITY_IDLE` (`0x401827..0x401868`), i.e. as
  fast as an otherwise idle machine allows.
* **VERIFIED:** modules pace themselves with the engine clock:
  `XTimer::GetMilliseconds`/`GetTicks` = `timeGetTime()` (`ADXPL510 0x420058`,
  `0x42005e`), `GetTicksPerSecond` = `1000 << 16` (16.16 fixed, `0x420064`),
  `XGetTimeAndDate` = CRT `time/localtime` (`0x42006a`). `timeGetTime` is the
  one clock our host must virtualize for the AD4 lane (a few modules also call
  `GetTickCount`/`GetLocalTime` directly — see API_SURFACE).
* **VERIFIED:** `XNoiseMaker::GiveTime` (per frame) re-reads volume and the
  sound bit each call (`0x427538`), so control refreshes take effect live.

**Encoding (VERIFIED by `research/win/adres.py` over all 84 Deluxe modules).** PE:
the numbered custom types are plain integer type ids in the resource

#### 2.10.2 Control record layout (type 1000) — VERIFIED

Parser: `AFTERDAR.SCR 0x4051cd` (dispatch), `0x404f7b` (kind 1),
`0x4050f4` (kind 2), `0x405149` (kind 3), `0x4051bb` (kind 5); UI:
`ADPAGE.DLL 0x9003e8d..0x9003ee6` (trackbar range/position),
`0x9003a34..0x9003a78` (value label). Byte-packed, little-endian:

```
+0x00 u16  kind      0 none  1 string slider  2 numeric slider  3 popup  4 button  5 checkbox
+0x02 char name[20]  (lstrcpyn(dst, rec+2, 20) — 19 chars max; "Display Karaoke" fits)
+0x16 u16  count     kinds 1,3 (host caps at 101)
+0x18 i16  default   kind 1: a stop VALUE; kind 2: the value (clamped to [min,max]);
                     kind 3: item index (clamped); kind 5: nonzero = checked
+0x20 char label[16] x count          kinds 1,3
kind 1: u16 values[count] immediately after the labels
kind 2: +0x20 char unit[16]; +0x30 i16 min; +0x32 i16 max; +0x34 u16 (unused by
        AFTERDAR/ADPAGE); +0x36 u16 unitPos: 0 "%d", 1 "%s%d" prefix, else "%d%s" suffix
```

**Kind 1 (string slider) table, VERIFIED `0x404f7b`:** if `values[0] != 0`
the host prepends a 0 and repeats the last label (flagged at `+0x670[n]`), so
the stop list is `(label_i, lower-bound value_i)`; the default stop is the
last stop whose value ≤ `default`. The flagged extra stop is a real, selectable
position: the control panel draws its label in a bold copy of the dialog font
(**VERIFIED `ADPAGE 0x90039fc`** tests the flag, **`0x9003ac8`** sets
`lfWeight = 700` before `CreateFontIndirectA`), so e.g. Flying Toasters Pro's
"Objects" reads Flight · Squadron · Air Wing · Swarm · **Swarm** with values
0/25/50/75/100. All 74 Classic string sliders store upper bounds
(`values[0] != 0`) and get this extra stop; no AD4 record does. The value sent is `values[stop]`
(`0x405234`) — a 0..100 position, which modules turn into a bucket with
`GetSliderValue(ctl, n) = (clamp(v,0,99)*n + n-1)/100` (**VERIFIED
`ADXPL510 0x42baed`**). Kind 3 sends the index (`GetMenuValue` clamps to
`n-1`, `0x42bb2b`); kind 2 sends the number; kind 5 sends 0/1; kind 4 has
no value (BUTTON message).

**Kind 2 caveat:** many Classic records carry `default` outside `[min,max]`
(e.g. Hard Rain "# of Drops" 1..9 default 22). The AD4 host clamps it
(**VERIFIED `0x4050f4`**) and ADPAGE uses `[min,max]` as the trackbar range
with the value as position (**VERIFIED `0x9003ea9..0x9003ee6`**); whether
the AD 3 control panel read `default` as a 0..100 position is
**UNVERIFIED** (the SDK's CONTROLS.TXT would say; not in our hands). Hard Rain
uses `iControlValue[0]` directly as a drop count (**VERIFIED
`CLASSIC/RAIN.AD 2:0020..2:0049`**). The catalog keeps both (`default`,
`rawDefault`).

### 3.1 How AFTERDAR.SCR drove a Classic module — VERIFIED

Classic module class (vtable `0x40f020`):

* **Message `0x401f6f`:** host message 4 → `SetWindowOrgEx(hdc,0,0,0)` +

### 3.2 OLDMOD32 → OLDMOD16 thunks — VERIFIED

`OLDMOD32.DLL` is `thunk.exe` output: each export narrows its arguments and
calls `QT_Thunk` with `CL` = index into OLDMOD16's `THUNK_THUNKDATA16` table;
flat pointers become 16:16 with `SMapLS_IP_EBP_n`; handles go through
`WOWHandle16(h, type)` (0 HWND, 4 HDC, 10 HPALETTE). The 16-bit side is
`PASCAL FAR` (arguments pushed left to right, callee pops).

| 32-bit export (cdecl) | CL | 16-bit export (ord) | 16-bit prototype (PASCAL FAR) | 16-bit evidence |
|---|---|---|---|---|
| `LoadADModule3216(HWND, HDC, int *ctrl, int volume, int mute, char *path, char *err, int errLen)` `0x9801054` | 6 | `LOADADMODULE16` (2) | `int (HWND, HDC, int FAR *ctrl4, int volume, int mute, LPSTR path, LPSTR err, int errLen, int FAR *errId)`; returns 1/0; on 0 with `*errId` the thunk does `LoadString(hOldmod32, errId, err, errLen)` | `1:0ec8`, `retf 0x1a` |

(`research/win/abiverify/nex.py`): every `retf` size, the `[bp+n]` argument
reads and the push order in `OLDMOD32` match the table. Frame after
`mov ax,DGROUP; enter`: `[bp+6]` is the **last** argument (e.g.
`LOADADMODULE16`: `[bp+0x1e]` HWND, `[bp+0x1c]` HDC, `[bp+0x18]` ctrl4,
`[bp+0x16]` volume, `[bp+0x14]` mute, `[bp+0x10]` path, `[bp+0xc]` err,
`[bp+0xa]` errLen, `[bp+6]` errId). `ctrl4` is **four 16-bit WORDs**:
`OLDMOD32` narrows the caller's 32-bit `int[4]` into a WORD array on its stack
before thunking (`0x98010a1..0x98010ad`, `0x98011aa..0x98011b6`).
`OLDMOD32` itself only null-checks `ctrl`, `path` and `err`.

`OLDMOD32`'s `DllMain` only calls `ThunkConnect32` (`0x9801000`).

**`OLDMOD16` must be initialized through `DLLENTRYPOINT` — VERIFIED
(abi-review).** Its NE header has **no entry point** (`CS:IP = 0:0000`) and
expected Windows version 4.00; all its initialization is in the exported
`DLLENTRYPOINT` (ord 1, `1:0000`, `retf 0x10`):
`BOOL FAR PASCAL DllEntryPoint(DWORD dwReason, WORD hInst, WORD wDS, WORD
wHeapSize, DWORD dwReserved1, WORD wReserved2)` — `dwReason` is the dword at
`[bp+0x12]`, `hInst` `[bp+0x10]`. For `dwReason == 1` it `GlobalAlloc`s
(`GMEM_MOVEABLE|GMEM_SHARE`) the `AD_SYSTEM` (0x3C) and `AD_MODULE` (0x30)
blocks and `GlobalLock`s them into `[0x11ec]`/`[0x11f0]` (`1:0110..1:019f`;
returns 0 if that fails) and keeps `hInst` in `[0x11ce]`; for `dwReason == 0`
it frees them (`1:01a0`). Either way it then returns the result of
`ThunkConnect16("oldmod16.dll", "oldmod32.dll", hInst, dwReason,
&THUNK_THUNKDATA16, "thunk_ThunkData32")` (`1:0051..1:0074` → `1:00e8`), so
that shim must return non-zero. The Win95 16-bit KERNEL called this export for
4.0-marked DLLs; that it does so automatically is our inference, not something
in these binaries — **our NE loader must call it explicitly** after loading
`OLDMOD16` (reason 1) and before unloading it (reason 0). Without the call
`hADSystem`/`hADModule` are 0 and `LOADADMODULE16` writes through null far
pointers. (`AD_SND.DLL` and the other Classic DLLs use the ordinary NE entry
point — `AD_SND` `CS:IP = 1:2dc0` — and do not export `DLLENTRYPOINT`.)

### 3.5 ADXPL300 (12 modules)

* **VERIFIED** entry `1:0000` is the Borland 16-bit DLL startup (`LocalInit`,

### 3.7 Recommendation for our 16-bit lane

Run `OLDMOD16.DLL` (and `AD_SND.DLL`, `ADXPL300.DLL`, helpers, module) as real
emulated code and replace only `OLDMOD32`: the host pushes the PASCAL
arguments of §3.2 on an emulated 16-bit stack and far-calls the NE entry
points (`LOADADMODULE16` etc., found by resident name) with a sentinel return
address, exactly as `QT_Thunk` would. Pointers passed in are 16:16 pointers to
emulated buffers (allocate them in a host-owned LDT segment); `HWND`/`HDC`/
`HPALETTE` are the 16-bit handles of our Win16 shim; `ThunkConnect16` →
return 1; `LoadString(hOldmod32, errId)` for error ids 1..3 can be replaced
by host-side strings ("cannot load ad_snd.dll", etc.). Nothing in OLDMOD16
needs a 32-bit process on the other side. Sequence: load `OLDMOD16` →
far-call `DLLENTRYPOINT(1, hInst, DGROUP, heap, 0, 0)` (it has no NE entry
point, §3.2) → `SETADPALETTE16` ×4 → `LOADADMODULE16` → per frame
`MODULEMESSAGE16(2)` → `UNLOADADMODULE16` → `DLLENTRYPOINT(0, …)`. Pass
`ctrl4` as four WORDs.

## 4. Surprises (all VERIFIED unless marked)

* **Two clocks, no pacing.** The 1996 host hammers DRAWFRAME at idle
  priority; AD4 modules pace with `timeGetTime`, Classic ones with
  `GetTickCount`/DOS/BIOS time.
* **Busy-waits and CPU-speed calibration on the clock.** Several binaries spin
  on a clock *inside one call*, so a virtual clock that advances only between
  frames would hang them. Found with `research/win/spinwait.py` (static
  heuristic, every hit read by hand; `spinwait.json`):

  | Binary | Where | What it does |
  |---|---|---|
  | `AD_RSRC.DLL` | ord 143 `2:4820`, called from its DLL init `1:0058` | **calibration**: wait for a `GetTickCount` edge, count calls until the next edge, store `n*18 + n/5` (≈ calls per second, assuming 18.2 edges/s = a 55 ms tick) at `[0x71c]` |
  | `AD_RSRC.DLL` | ord 144 `2:48a0` (imported by 6 modules) | calibrated delay: `us * [0x71c] / 1e6` calls to `GetTickCount` |
  | `CLASSIC/EINSTEIN.AD` | `2:0078..2:00b8` | same calibration (count × 18 / 60) |
  | `CLASSIC/LUNATIC.AD` | `54:0094..54:00ea` | measures the tick granularity (ms between edges) and loops per edge; `54:0167` delay loop, `54:0412` wait for an edge, `32:0ca8` `while (now - t0 < n)` |
  | `AD40/PSYCHO.AD` | `0x4117c2..0x4117d6` | after `ExtTextOutA` of a message: `while (GetTickCount() < t0 + 2500)` — a 2.5 s spin |
  | `AD40/CYBER.AD` | `0x411465` | `while (GetMilliseconds() < base + k*i)` |
  | `ADXPL510.DLL` | `0x4102eb..0x410306` | time-sliced work loop until a `GetMilliseconds` deadline |
  | `CLASSIC/TUNNEL.AD` | `1:16fe`, `1:1214..1:125e` | frame limiter spinning on `GetCurrentTime`; draw loop bounded by time |
  | `CLASSIC/PHOTON.AD` | `2:0421` | `while (timeGetTime() <= t0 + d)` |
  | `CLASSIC/EINSTEIN.AD` | `2:1b13` | waits for a sound's duration after `adwPlaySound` |
  | `CLASSIC/FRACTAL.AD`, `MOUNTAIN.AD`, `SATORI.AD` | `1:65f6`/`1:6686`; `2:1faa`; `2:1b33`/`2:1c0d` | compute in slices until an 83 ms / time / 3 ms deadline |

  (GRAVITY/GEOBOUNC/PUZZLE/SPIRAL/WORMS/SATORI `2:0xxx` "has the tick
  changed?" checks return instead of spinning — not busy-waits.)
  **Consequence for `VirtualClock`:** every clock read (`timeGetTime`,
  `GetTickCount`/`GetCurrentTime`, INT 1Ah, INT 21h AH=2Ch,
  `GetLocalTime`/`GetSystemTime`) must advance virtual time monotonically — e.g.
  by a fixed small step per read on top of the per-frame tick — which stays
  deterministic. The calibrations assume Win 3.x/9x-style coarse ticks
  (18.2/s, an inference from the constant 18): if 16-bit `GetTickCount` is
  1 ms-granular *and* advances 1 ms per read, AD_RSRC measures 1 call per edge
  and its delays shrink ×55; quantizing the Win16 tick to 55 ms while advancing
  1 ms per read reproduces the original ratio.
* **Classic modules were Win9x-only by design** (host `0x405f21`) and relied
  on Win9x VDD port virtualization (VGA DAC and retrace ports), BIOS
  selector `0x40`, INT 21h/1Ah/2Fh/25h.
* **Borland per-thread slots below the stack base.** Every Borland PE
  (engine + all 22 AD40 modules) reads/writes `[FS:[4]-8]` and `[FS:[4]-4]` in its DLL
  entry and exception code (31 `FS:[4]` sites each). Our TEB must have a real
  `StackBase` with writable dwords below it.
* **Address-size prefix and x87 in flat 32-bit code.** Every Borland PE
  (engine + all 22 AD40 modules; not the MSVC `STARRYNI.AD`) reaches the TIB with
  `0x67`-prefixed 16-bit addressing — `64 67 A1 00 00` `mov eax, fs:[0]`,
  `64 67 A3 00 00`, `64 67 8B 16 04 00` `mov edx, fs:[4]` (272 sites across
  the lane; e.g. `ADXPL510 0x410064`) — and its math RTL uses `67 E3 rel8`,
  i.e. **`jcxz` testing CX, not ECX**, between x87 compares
  (`ADXPL510 0x443401..0x443420`: `fnstsw [esp+2]; jcxz; fxch; wait; sahf`).
  x87 is needed in the flat lane too: hundreds of x87 instructions per binary
  (the exact count depends on how the sweep resynchronises after data in
  `CODE`: ~620/~660/~300 for `ADXPL510`/`PSYCHO`/`TOASTERS` with `pedis.py`,
  416/449/155 with the plain sweep of `abiverify/prefix67.py`; `SWIRLING` and
  `MARBLES` are also x87-heavy). The 272 `64 67` sites and 31 `FS:[4]`
  references per Borland image were re-counted by byte pattern
  (abi-review). The flat CPU
  must decode ModRM with 16-bit addressing under `0x67` (base 0 FS, disp16)
  and honour `0x67` on `jcxz`/`loop`/string ops.
* **SEH + longjmp exceptions.** `PushFarCatch/FarThrow/PopFarCatch`
  (`ADXPL510 0x41bd9c..0x41be04`) keep a 16-deep handler stack;
  `FarCatch` longjmps (`0x444b6a`) using a Borland `setjmp` buffer that
  saves `FS:[0]` (`0x444b34`) and calls **`RtlUnwind`** when the SEH chain
  differs. C++ `throw` uses `RaiseException` (`0x43f172`). FS:[0] chain walking
  and `RtlUnwind` semantics are required.
* **DirectSound, dynamically.** Not in any import table.
* **CD audio window** `"blargCD"` with MCI alias `qwanza`.
* **Mouse message mismatch**: the SDK dispatcher handles 21/24/27/30; the
  saver sends 10–15.
* **Mini-preview blocklist**: in `/p` mode the host refuses to animate modules
  whose `2000/20` name is in a table of 59 names (other After Dark editions:
  Star Trek, Simpsons, Disney, Marvel…) and draws a static preview instead
  (`0x401bbb`, table `0x4103d8`).
* **"BUTTHEAD"** signature in `AD_SYSTEM` checked by Classic modules.
* **Classic modules write engine data directly** (ADXPL300 exported
  variables).
* **Self-modifying code**: none found — no writes through CS: overrides in
  reachable code, no `AllocCStoDSAlias`/`PrestoChangoSelector` imports.
  Threads: only the host's runner thread (the engine creates none).
  `SetTimer`: 1 Classic binary.
